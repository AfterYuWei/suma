# 持续交付与项目 CD：需求重评及发布体验重设计

日期：2026-11-14。状态：代码已实现，远端 Go／Web 门禁、183 项 Web 单元测试、490 个唯一浏览器用例、发布并发检测、真实 CD Docker 业务及隔离数据库升级／恢复演练已通过。按用户要求不进行本地测试；本文不替代已落地的任务中心契约。详见 [验收记录](cd-release-validation-2026-11-14.md)。

## 1. 产品结论

现有问题主要来自操作模型：用户想发布一个确定的版本，界面却要求先理解两套模块、Git 同步、Release、应用、记录、策略及自动触发。正常路径需要用户手动串联，异常路径又会改变配置和镜像的使用规则。

推荐保留两个业务入口，统一发布语言、操作流程和结果表达：

- **持续交付**：管理一个交付项目对多个明确节点的发布。
- **节点项目 → 发布**：管理当前节点、当前项目的 Git 交付；替换用户可见的「CD」标签。
- **任务中心**：继续统一触发、调度、任务进度和跨业务追溯，不成为第三套发布配置或业务历史。

用户的主流程统一为：**点击「发布…」→ 审阅本次变更与目标 → 确认发布 → 在原位置看结果**。检查、固定 Commit、解析镜像、校验凭据和生成预览由系统完成；不要求先手动同步再找 Release。

两个入口统一体验，不在本次设计中强制合并业务表、迁移项目身份或重写执行器。

## 3. 最需要解决的六个问题

| 优先级 | 用户困惑 | 根因 | 新设计 |
| --- | --- | --- | --- |
| P0 | 我要发布，为什么先点同步，再去另一个标签找版本？ | 技术步骤成为用户工作流。 | 主入口「发布…」自动准备预览；「检查更新」保留为只读辅助动作。 |
| P0 | 持续交付的发布和项目 CD 的应用有什么区别？ | 同一意图使用两套词汇与页面组织。 | 均使用发布、发布记录、恢复版本；单节点入口固定目标。 |
| P0 | 我看到的这个版本，点下去到底会用哪份配置？ | Git 版本与本次配置混在 Release 上，预览和执行之间没有显式契约。 | 本次发布同时固定 Git、配置、镜像及节点；确认绑定这份方案。 |
| P0 | 配置里还是 `latest`，为什么回滚后不是原来的镜像？ | 配置恢复与镜像版本恢复被统称为回滚。 | 新发布固定镜像 digest；历史缺少证据时只能明确「重新应用历史配置」。 |
| P0 | 三台成功一台失败，现在整个项目算什么状态？ | Release、一次操作与各节点运行态互相覆盖。 | 分开显示本次结果和当前运行；失败节点直接处理，成功节点默认不重做。 |
| P1 | 观察、手动、自动、总开关和周期开关怎么组合？ | 策略、触发方式、暂停及首次保护没有形成一句可读说明。 | 分组配置，并汇总成「每 5 分钟检查，有更新等待确认；Webhook 开启」。 |

补充判断：检查记录应可追溯，但不应淹没发布记录；保存变量或自动化设置不应让用户误以为运行容器已经改变。

## 5. 用户只需要理解三个对象

| 用户概念 | 含义 | 不应承担的职责 |
| --- | --- | --- |
| Git 版本 | 仓库中的固定 Commit 及其文件。可显示提交说明、短 SHA、分支／Tag。 | 不代表某次部署完整输入，不代表运行健康。 |
| 本次发布 | 一份可审阅、确认后固定的发布方案，以及这次执行产生的记录。 | 不能在确认后偷偷换成更新的配置、节点或标签内容。 |
| 当前运行 | 每个节点、服务当前实际运行的镜像、配置对应关系、健康与观察时间。 | 不能由最近一次操作成功或 Commit 相同推断。 |

「发布方案」是操作过程中的摘要和快照，不新增顶级导航或要求用户手动管理草稿对象。项目 CD 不为此创建全局交付项目；全局已有 Release 的去重与历史编号保持原样。

每次方案至少固定：项目来源身份、Commit、Compose 文件内容及合并顺序、依赖文件、本地覆盖变量、配置版本、目标节点身份、凭据引用、部署超时、失败恢复策略，以及每个服务适用平台的镜像 digest。

变量以现有密钥加密；普通预览只显示变量名及新增／修改／删除，不输出明文，也不公开可枚举低熵秘密的单项指纹。凭据只固定引用及授权要求，不复制过期令牌来绕过当前权限校验。

## 6. 信息架构及页面

### 6.1 持续交付列表

每行优先回答：项目名、当前运行摘要、待发布变更、最近发布结果、自动发布状态。

示例：`eizhu-admin · 3/4 节点运行 #185，1 节点待确认 · 有更新 · 上次部分失败 · 手动确认`。

不再把 Commit 已同步显示为整体「已同步」。Git 最近检查时间放在次级信息中。节点不可读时显示未知及最后观察时间，不能纳入健康计数。

第一阶段保留现有全局交付项目列表；节点项目 CD 仍从节点进入，统一记录继续汇总两类来源。将两类项目合并成全局发布对象目录属于后续范围，不能靠 UI 合并造成双重归属。

### 6.2 项目详情：三个标签

- **发布**：默认页，包含当前运行、待发布变化、当前发布进度或最近失败、节点结果。
- **发布记录**：按一次实际变更操作排列，包含发布、重试、恢复和自动恢复；每条保留其原始结果。
- **设置**：来源与认证、目标、变量、自动化、超时和恢复策略。

全局详情用上述三标签替代概览／Release／记录／设置四分法；Git 历史版本作为发布面板中的版本选择器，不再是日常发布必经页面。

节点项目保留配置、服务、日志等既有能力。项目内「发布」页默认展示运行及发布操作，长期 CD 配置通过本页的「发布设置」进入，避免再嵌套一排全局式标签。原 CD 深链接兼容跳转；由全局交付拥有的运行项目只能跳转到其所属交付项目，不能再建立独立来源。

运行信息用紧凑对齐列表，功能区使用轻背景；保留暗／亮主题，不使用卡片仪表盘、细分割线或每行一串操作按钮。

### 6.3 统一发布面板

点击「发布…」后，在同一 Sheet／大屏面板中完成准备、审阅和进度：

1. 系统读取当前已保存配置，解析所选引用到固定 Commit，读取文件、解析镜像、校验目标及授权。此阶段标记「准备发布」，不改变运行容器。
2. 显示「当前 → 本次」摘要：代码是否变化、镜像变化、配置变化、将新增／重建／移除的服务、所选节点及对应当前版本。
3. 展开时才查看逐文件差异、变量名称变更、完整 digest、凭据引用及执行策略。不同节点基线不同，逐节点展开，不伪造一个统一旧版本。
4. 底部主按钮明确为「发布到 3 个节点」或「发布到当前节点」。完成一次最终确认，不再追加泛化的“确定吗”。
5. 提交成功后原面板变为同一次发布进度；可收起到后台，再打开继续看同一记录。

默认使用已配置节点；本次可以取消选择其中部分节点，不增加或删除项目长期目标。新增目标先去设置保存。排除离线节点必须显式显示剩余范围，不静默缩小。

准备失败逐项展示：节点不可达、镜像不存在／平台不匹配、认证失效、Compose 不符合限制等；用户可修正后重新准备。任何阻断项均不可确认发布。

有未保存配置时给出「保存并准备发布」及「继续编辑」，不丢草稿、不隐式使用旧值。已保存设置本身不会自动部署；保存成功继续准备也必须再经过发布确认。

## 7. 发布及异常场景契约

### 7.1 首次创建和首次关联

新建全局交付项目默认手动确认。完成必填配置后提供「保存并准备首次发布」及低强调「仅保存」；前者只创建项目并准备预览，用户确认前不启动部署。

现有节点项目启用 Git 来源先审阅原 `.env`，保留现有导入约束。关联成功后直接进入首次发布预览，显示现有运行与仓库配置差异。首次发布及仓库／引用／文件范围变化仍需人工确认，不能由自动策略绕过。

### 7.2 发布新 Git 版本

用户无需先同步。版本默认选择已配置引用的最新可用 Commit，也可选择已发现的历史 Commit。准备时解析并固定；后台出现更晚 Commit 只提示，不替换正在审阅的方案。

「检查更新」始终只更新候选及检查证据，即使启用自动发布，也不把这次人工只读动作隐式转换为部署。自动调度和 Webhook 按已保存策略运行。

### 7.3 Git 未变，但镜像或变量变化

「发布…」同时检查声明镜像的 digest。Git 不变、可变镜像标签指向新内容时，预览明确显示「代码未变化，镜像有更新」，无需制造新 Commit 或新 Git Release。

已保存变量变化时显示「代码未变化，配置有更新」，使用新配置生成本次方案。记录独立于 Git 版本，完整保存本次快照。

Git、有效配置、镜像和节点状态均无变化时显示「没有待发布变更」，不默认重建。确需重建时展开「高级 → 即使无变化也重建」，明确范围和影响，并形成新的执行记录。

本阶段只新增人工准备时的镜像检查，不新增 CD 镜像周期触发器；项目 CD 继续暂停普通镜像自动更新，避免两个入口抢占同一项目。

### 7.4 部分失败与重试

结果示例：「本次发布：2 成功、1 失败；当前运行：2 新版、1 状态待确认」。错误直接显示节点名、失败阶段、安全错误摘要和日志入口，不要求先去任务中心找 ID。

主要操作「重试失败节点（1）」直接基于该发布记录，不再从 Git Release 中猜来源。重试使用原方案的 Commit、配置和镜像 digest，只重试当前仍符合条件的失败节点；重新校验当前授权、节点身份及运行变化。

修改过设置时并列说明「本次重试使用原发布配置；要应用新设置，请发起新发布」。提供次级「使用新设置发布…」，不能把修正后的变量静默注入旧重试。

原发布的失败结果永久保留，新重试通过来源记录关联。页面可以汇总「后续已修复」，但不得把原记录覆盖为成功。

### 7.5 恢复版本

常用操作从历史**成功发布记录**开始，文案为「恢复到发布 #184」。先审阅目标节点、将恢复的配置及镜像，再确认。原记录中失败或未执行的节点不是有效恢复来源。

另提供「恢复失败节点」时，默认只涵盖本次已经改变且存在可靠前序成功快照的失败节点，逐行显示其各自目标；恢复目标可能不同。需要恢复本次成功节点时由用户显式选择，不把“失败恢复”扩大成全量恢复。

恢复及失败自动恢复都使用冻结的旧镜像 digest，不重新解析旧标签。旧镜像不可获取、快照不完整或凭据失效时阻止相应节点恢复，不能悄悄拉最新内容。发布前检查可恢复性并显示“哪些节点没有可恢复基线”；这不会被描述成一定可成功回滚。

恢复前以事务将自动发布策略切为手动确认，周期和 Webhook 可继续检查；页面明确显示「自动发布已暂停，检查继续」，人工重新开启前不因下一次检查发布坏版本。恢复失败也保留此保护。

历史记录缺少 digest 时保留可读证据，在高级操作中提供「重新应用历史配置」，明确标签将使用当前仓库内容。该操作不能使用「恢复原版本」文案，也不能纳入可靠自动恢复。

恢复范围是应用配置和容器镜像，保留数据卷，不回退数据库内容。若应用版本包含不兼容的数据变更，SUMA 不能据容器健康声称业务已恢复。

### 7.6 执行、取消及健康

阶段统一为：校验 → 拉取镜像 → 更新容器 → 检查运行状态。按节点展示真实阶段和已知进度，不按日志行数制造总百分比。

健康检查有配置时显示检查结果；未配置时显示「容器运行，未配置健康检查」，不能宣称业务健康。节点离线显示未知，不用历史成功填充。

收起面板不取消任务。可取消的操作提供「停止后续执行」，明确已完成的 Docker 变更不会自动撤销；取消后按节点重新观察，记录部分结果。仍保持现有 Task 的状态契约，业务摘要表达部分完成。

## 8. 自动化：减少组合猜测，不删掉控制能力

设置分为三个相邻小节：

| 配置 | 选项／语义 |
| --- | --- |
| 更新后如何处理 | 仅检查（保留现 observe，不允许人工发布）；手动确认；自动发布。观察模式旁明确说明“需切换策略才能发布”，不能只放一个无解释的禁用按钮。 |
| 何时检查 | 周期间隔与 Webhook，显示下次检查及最近触发结果；配置入口与任务中心共用同一规则及版本。 |
| 暂停什么 | 暂停周期检查；暂停全部自动触发。明确 Webhook 是否仍生效、已开始任务继续。 |

项目页显示一句有效状态，例如「每 5 分钟检查 + Webhook；发现更新等待确认」。自动模式尚未首次确认时显示「首次发布待人工确认」；暂停时不能仍只显示“自动发布已开启”。

不新增独立调度器，不改变忙时跳过、重启不补跑、Webhook 验签／去重及触发历史契约；定时事件不积压成待发布队列。

自动发布也必须生成相同固定方案、保留同等变更摘要和节点结果。准备后配置变更则本次中止并留证，等待下一有效触发；不偷偷改用新配置。

## 9. 发布确认的可靠性

这里需要的复杂度来自已存在的具体失败路径：用户预览后他人修改变量或目标、`latest` 在检查和拉取间移动、重试套用新设置，以及节点迁移后同一 ID 指向另一 Engine。代价是增加一份受控发布快照和确认校验；可以复用现有配置版本、快照、节点绑定及 registry digest 能力。

- 准备结果绑定业务配置版本和目标身份，初始建议有效期 10 分钟；失效后在原面板重新准备并展示差异。
- 确认后执行只读取冻结输入；配置或策略在确认前改变时返回冲突并保留用户选择，不自动提交新方案。
- 对人工操作重复点击／请求重送返回同一次记录，不能重复部署；不承诺外部 Docker 副作用恰好一次。
- 可变标签在准备时解析成固定引用；执行只拉取所选 digest，不能重新按标签挑选新镜像。多架构要记录镜像索引及各目标平台对应 digest，不能把 amd64 的结果用于 arm64。
- 当前授权、节点启用状态及 Engine 绑定在执行前仍需复核；失效应明确失败，不能借历史凭据绕过。
- 运行态必须来自当前节点 Docker；历史记录和 Task 是执行证据，不是容器实时状态的替代品。

digest 的不可变性及多平台含义参见 [Docker 官方说明](https://docs.docker.com/dhi/explore/security-concepts/digests/)。上述规则为产品要求，本次代码按此实现，正确性仍待测试环境验证。

## 11. 可验收标准

以下为验收标准。服务、迁移、浏览器及 CD Docker 业务已有远端验收证据，具体覆盖和环境限制见验收记录；不把旧统计冒烟失败或未单独执行的场景算作通过：

1. 从全局项目详情或节点项目打开发布，均无需先点同步或切到 Git 版本页；正常路径只需「发布…」和一次范围明确的确认。
2. 创建或关联后可连续进入首次预览；保存和预览阶段不产生容器变更；首次自动发布保护保留。
3. 用户能在确认前读出 Commit、配置是否变化、镜像是否变化、哪些节点／服务会改变；秘密默认隐藏。
4. Git 不变而镜像标签内容变化、仅变量变化，均可发起新发布记录，不新增重复 Git Release。
5. 预览后 Git 分支或镜像标签移动，不改变待确认／执行内容；配置、目标或策略改变则明确冲突重新准备。
6. 连续确认及网络重送不创建重复部署；离开再进入可以打开原发布进度。
7. 多节点部分失败可直接定位节点、失败阶段和原因；重试只作用于符合条件的失败节点并沿用原输入。
8. 改设置后的重试明确保留原配置；用户可以另行用新设置发布，两个意图不能混淆。
9. 恢复到成功记录使用原镜像内容；历史缺少 digest、旧镜像不可获取及授权失效分别展示真实限制；不伪造“恢复成功”。
10. 恢复／自动恢复后保持人工确认策略，失败证据不被改写；数据卷和数据库业务数据不回退。
11. 运行态、一次操作结果、自动触发状态分开；无健康检查与节点不可达均不会显示为已健康。
12. 两入口中英文、深浅主题、320／390／1440px 可读；单节点面板不出现无意义节点选择器；键盘、长项目名、长错误及打开菜单实际几何通过。
13. 完整实现按项目规则执行 Web／Go 全门禁、完整浏览器回归及独立 Unix／mTLS TCP／HTTPS-WSS Agent 真实 Docker 验收；数据库变化另验证空库和保留数据升级。

可用性验证建议：请实际操作用户完成“首次发布、镜像更新但代码不变、部分失败恢复”三项任务，记录误操作、返回设置／任务中心次数和是否能准确复述本次输入。没有基线前不声称效率提升百分比。
