# 任务中心与业务自动化统一：最终设计

初稿：2026-11-12；定稿：2026-11-13。状态：方案实现及任务中心验收已完成，尚未部署生产。

本文是 `feat/task-center` 后续实施的需求、行为与兼容性依据，替代此前仅修复九个缺陷及两项查询优化的实施范围。需求与兼容性约束以本文为准；完成情况及实际验证边界见下方当前落地状态与验证记录。

本次按“统一规则与触发、复用业务执行”的方案交付。下表为最终决策，后文给出执行契约和验收依据；实现未达到这些约束时继续修复，不以缩减验收范围代替完成。

| 决策 | 最终选择 |
| --- | --- |
| 交付范围 | 镜像更新、存储清理、全局 CD、节点项目 CD 四类一次统一；不只交付镜像更新。 |
| 调度归属 | Task Center 是唯一周期派发方；Task 是唯一执行状态来源；业务保留授权、锁、配置及业务历史。 |
| 配置入口 | 中心和原业务入口读写同一份规则，经业务校验后事务更新兼容投影；不保留两套调度配置。 |
| 忙时与重启 | 忙时跳过且推进周期，不排队；Cron 不补跑，CD interval 最多进行一次当前检查。 |
| 暂停与手动 | 分开提供“暂停周期”和“暂停全部自动触发”；CD 手动检查只刷新候选，发布仍走原业务确认。 |
| 数据与发布 | 新增增量迁移、归档保留证据；四类适配器和调度切换匹配发布，全部验收通过才标记完成。 |

## 1. 交付目标与范围

运维人员应能在任务中心回答：现在执行什么、下一次何时触发、为什么执行或未执行、实际改变了什么。一次交付完成四类业务自动化的调度、触发、启停和执行历史统一。

| kind | 业务及目标 | 自动触发 | 业务仍负责的内容 |
| --- | --- | --- | --- |
| `image.update` | 节点上的托管 Compose 项目 | Cron | 检测／自动更新、服务选择、仓库授权、digest 与配置重验 |
| `system.cleanup` | 单节点存储清理策略 | 每日／每周，按 Cron 存储 | 删除授权、预览、保留期、保护资源、资源逐项重验；卷只允许手动确认删除 |
| `cd.sync` | 全局多节点交付项目 | 30–86400 秒间隔、Webhook | 仓库、候选、观察／手动／自动策略、首次确认、多节点编排、回滚 |
| `project.cd.check` | 节点项目 CD | 30–86400 秒间隔、Webhook | 仓库、候选、首次确认、项目锁、部署模式、失败自动恢复 |

- 所有现有 Docker、Compose、CD 长操作继续使用 Task；人工发布、回滚等操作继续通过原业务服务执行并进入统一执行历史。
- Agent 心跳、节点探测、监控采样、实时流刷新、通知投递重试和预览 TTL 属于所属模块的后台生命周期，不变成用户可编辑的自动化规则。其产生的长操作仍记录 Task。
- 采用现有单体服务、PostgreSQL、ComposeRunner 和前端组件；不引入消息队列、工作流引擎、通用 DAG、第三方调度服务或新的任务执行进程。

## 2. 职责与唯一配置来源

1. **Task 服务**负责执行生命周期、进度、日志、步骤、取消、入参快照和结构化结果；Docker 当前状态仍以目标节点 Engine 为准。
2. **Task Center**负责自动化规则、唯一周期扫描器、触发认领、触发历史、运行关联和跨业务查询。
3. **业务服务**负责参数归一化、操作授权、安全条件、业务状态及业务历史。中心不得通过直接更新数据库或直接调用 Docker 绕过这些条件。
4. **业务入口与中心入口**使用同一套专用编辑组件和服务方法。中心不提供任意 JSON 编辑器；kind 注册包含适用范围、支持的触发方式、允许的操作和前端编辑／结果视图。

规则中的自动化总开关、周期类型、周期参数和下一次时间是调度配置的事实来源。清理策略、仓库、凭据、交付策略与加密业务快照仍归业务表。

原 `automation_enabled`、清理配置中的启用／周期、`sync_interval_seconds` 与 `next_run_at` 字段保留为兼容投影。CD 的 automation_enabled 投影总开关；清理没有事件触发，其旧 Enabled 投影“总开关且周期开关”，旧清理启停请求同时设置这两个开关。既有 API 的写入必须经同一业务校验入口，在一个数据库事务中更新规则和投影；不得存在各写一份、定时互相同步的逻辑。Webhook 配置、验签密钥和来源去重继续由 CD 业务拥有。

规则增加只读的 `webhook_enabled` 投影，用于展示有效触发方式和派发门禁；它只能由 CD 业务配置事务更新，不能通过通用规则接口另设开关。是否接受 Webhook 由“规则未归档且总开关开启且业务 Webhook 配置启用”共同决定；周期开关不参与该判断。业务入口与中心入口对共享自动化配置使用同一配置版本契约，过期编辑返回 409，不能由旧业务表的值覆盖新规则。

清理和 CD 规则由有效业务配置建立或更新。中心的新建入口打开对应业务编辑流程；没有清理授权或有效仓库配置时，不能直接创建可执行规则。kind 的业务参数只存目标及配置引用，不存密钥或可执行命令。

## 3. 页面与操作语义

任务中心保留三个视图：

| 视图 | 内容 | 主要操作 |
| --- | --- | --- |
| 执行中 | pending／running；取消中沿用 running 并显示明确消息 | 查看进度、查看关联执行、取消支持取消的操作 |
| 自动化 | 四类业务规则、触发方式、有效状态、下次时间、最近触发结果 | 专用表单编辑、暂停、立即检查／运行、触发历史、归档 |
| 执行历史 | success／failed／canceled 及业务部分完成摘要 | 搜索、筛选、服务端分页、结果／日志／业务来源跳转 |

- 三个视图共享“当前节点／控制平面／全部”范围。全局多节点 CD 的主任务属于控制平面，节点子任务属于对应节点；任务详情可跳转关联父／子任务，不受当前列表筛选限制。
- 选择“当前节点”但没有选中节点时，显示选择节点提示，不隐式扩大到全部；切换范围、节点或筛选后，各视图回到第一页。
- 自动化规则详情展示触发历史，包括没有创建 Task 的跳过、拒绝和启动失败；触发记录链接 Task，Task 链接原项目、清理运行或交付记录。
- 列表优先显示业务名称、动作、来源和结果摘要，原始入参／结果 JSON 在详情中展开。复用现有节点选择、分页、Sheet、错误状态和紧凑样式。
- **暂停周期触发**：仅关闭规则的周期触发，Webhook 保持原设置。**暂停全部自动触发**：关闭自动化总开关，同时阻止周期和 Webhook。已启动操作可正常结束；取消是独立动作。
- **恢复自动触发**：保留原周期及 Webhook 配置，但重新经过业务校验。清理重新启用仍要求现有节点名确认与删除授权，不能借中心开关复用无效授权。
- **手动操作**：不改变周期；“立即检查”对 CD 只生成／刷新候选，不隐式发布，发布继续走业务确认。清理仍使用真实预览和现有确认；镜像立即更新保留重建确认和 Docker socket 授权。
- **归档规则**：停止未来触发，保留规则、触发、Task 和 Audit。业务删除时在原删除流程中归档规则。清理／CD 仍存在业务配置时，使用暂停；关闭其业务配置后才允许归档，防止无规则的有效配置被后台重新创建。
- 镜像设置同时提供“仅检测／检测并自动更新”和服务范围；保存周期不隐式启用已关闭规则。两处入口编辑同一配置。
- 表单在首次数据加载完成后初始化。编辑中的草稿与起始版本保持不变，轮询不覆盖；409 保留草稿并提供重新加载。新建计划先计算 kind 再计算节点要求，消除初始化错误。

有效状态由服务端派生：已归档、全部暂停、周期暂停、正常启用、已停摆。周期暂停时同时显示 Webhook 是否仍有效；总开关与周期开关均开启、周期类型非 none 却无下一次时间，或 kind 未注册、业务绑定失效时显示停摆原因，不能只显示一个“已启用”开关。

## 4. 调度、触发与并发契约

### 4.1 周期与恢复

- 保留一个 15 秒周期扫描器。Cron 支持现有五段表达式、已支持的描述符和 IANA 时区；interval 精确保留秒数，不能转换成分钟 Cron。
- 清理仅开放既有每日／每周配置。其 kind 的下一次时间计算复用现有民用时间算法：夏令时缺失时刻跳过、重复时刻只执行第一次。算法通过 kind 注册参与中心调度，清理不再保有独立扫描循环。
- 普通 interval 下一次时间为本次认领时间加间隔，不追赶积压；Cron 下一次为当前时间之后的有效时间。周期延迟达到 60 秒则记录 `missed_window` 并跳过，直接推进到未来时间。
- Cron 计划在重启后记录一次停机错过摘要并跳过积压；不补跑镜像重建或清理删除。CD 间隔规则在重启后最多发起一次基于当前配置的重新检查，再恢复正常间隔，不重放旧发布。
- 启动先执行原业务恢复：中断记录如实保留，项目 CD 原有中断后暂停行为继续有效。未知 kind、无效周期或失效业务绑定显示“已停摆”及原因，不伪装成正常启用。
- 启停、编辑和认领均检查版本及实际影响行数。调度推进不增加配置版本；用户配置变化才增加版本，避免正常周期使编辑草稿无端过期。

### 4.2 一次触发的生命周期

统一内部入口为 `Dispatch`，接收 kind／目标或规则 ID、来源、来源 ID、actor、手动动作与已验证参数；四类自动化的对应手动检查／运行、周期和有效 Webhook 均使用该入口。对应业务公开入口委托它，kind 回调调用内部启动函数，避免递归调用和重复记录。人工发布、回滚、容器／文件等其他操作保留业务入口和 Task 历史，不为每次操作新建自动化规则。

1. 短事务锁定规则，校验归档／总开关／周期开关／版本；检查本目标已有 dispatching 或活动 Task。周期认领和插入触发记录在同一事务提交，离开事务后再进行网络或业务启动准备。
2. 同一规则活动时，新自动触发记录为 `skipped/busy`；手动触发返回 409 并记录拒绝。不排队、不并行重放。无规则的临时镜像请求也必须在业务目标的 admission 临界区完成 busy 检查与任务创建。
3. 业务启动前再次检查当前授权和配置版本。Task 行创建、触发记录关联和 `dispatching → started` 在同一事务完成，提交后才启动工作 goroutine。`StartRequest` 传递触发记录 ID，`StartDefinition` 接收该可选关联；旧调用方不受影响。
4. 启动前失败记录 `start_failed`；正常启动后，实际执行状态只来自 Task，触发表不复制另一套执行终态。
5. 认领后、启动前进程中断的记录在重启时标记 `interrupted`，不重新派发。外部操作不能宣称 exactly-once；采用“每个周期最多认领一次、启动中断不重放”的契约。

业务执行门禁是暂停与启动的分界：尚未通过门禁的触发，即使已经创建 pending Task，也必须复核当前配置与授权；通过门禁的操作可以正常收尾，后续暂停不等同于取消。门禁拒绝时记录未执行原因，不伪造成功或产生业务副作用。对业务目标已删除、持久化配置无法解析等确定失效条件，留下启动失败证据并停摆对应周期；不得每 15 秒反复尝试同一坏配置。数据库暂不可读、节点离线或远端暂不可达按暂时启动失败处理，数据库可写时留证，不可写时按第 5 节上报；恢复后等待正常周期，不另加自动重试或永久停摆。

现有 Compose／CD／清理目标锁和资源预留继续有效，负责不同入口或不同 kind 对同一资源的冲突。自动发布、失败恢复是业务内部执行链，关联父／子任务，不拆成独立 Cron。

Webhook 在业务侧完成验签、仓库／ref 匹配及来源 ID 去重后派发；重复事件沿用既有证据，不创建第二个执行。匹配到有效规则但被暂停的事件记录 `skipped/automation_paused`。无效签名或不匹配事件不制造任务记录，沿用原安全处理。

### 4.3 可追溯信息

触发来源为 `manual | scheduled | webhook | system`，周期快照区分 Cron 和 interval。触发状态为 `dispatching | started | skipped | start_failed | interrupted`。

每条新记录保存：规则／业务目标、来源 ID、计划时间（适用时）、实际触发时间、actor、原因码、规则快照、业务配置版本及 Task 关联。快照不含 Webhook payload、密码或敏感环境值；业务历史继续保留其原有完整加密快照。任务中心只引用原 ID，不复制或替代 Release、CleanupRun、ProjectCDRecord。

## 5. 执行安全、结果与可观测性

- Docker 盘点、运行校验与 ComposeRunner 必须使用同一显式目标节点。修复镜像更新装配时传入本地默认 engine 的问题，覆盖 Unix、mTLS TCP 和 HTTPS/WSS Agent。
- 托管项目通过 ComposeRunner 解析声明镜像与 revision，跟踪声明标签，以实际容器 ImageID 对比远端。SUMA 重建产生的 digest 引用不终止后续检查；用户配置本身钉定 digest 时继续排除。
- 检测时捕获 revision，更新时使用同一 revision；拉取前与重建前均实际重验远端 digest，移除阻止第二次验证的 `sync.Once`。保留 one-off、非运行、CD 占用、混合副本和镜像漂移排除条件。外部项目保留仅检测运行时标签的能力，自动更新仍要求托管配置。
- 父任务取消／超时立即取消其镜像更新子任务，等待子任务退出与收尾完成后再写父任务终态。HTTP 请求结束不取消后台任务；取消不自动回滚已提交的 Docker 操作。父协程独占 summary，消除子回调并发写入。
- Task 的业务状态继续使用现有五种状态；“部分完成”通过业务结果明示。增加独立 `result_error`，区分执行失败与结果记录异常；不能因结果超限把已经成功的部署显示为执行失败。
- 入参上限 **8KiB**：在启动前明确拒绝超限参数。规则保存 typed、归一化的执行参数；日志快照采用结构化脱敏，不能通过改写 JSON 文本破坏合法性或执行语义。
- 结果和 artifact 上限统一为 **1MiB**：范围内完整保存；不逐字符截断，不丢服务项。极端超限或序列化失败保留实际执行状态，结果为空，写入 `result_error` 与安全错误日志，页面提示结果不可用、检查实际状态后再决定操作。
- `Task.result` 是新执行结果的事实来源；artifact 是按业务目标查询的投影，不拥有独立执行状态。投影保存失败不覆盖执行结果，详情／项目最近结果可读取对应 Task；历史已有 artifact 原样保留。
- Task 终态、结果、错误说明和最终日志优先事务写入。事务失败时使用独立 5 秒 context 尝试保存终态和安全错误证据；数据库不可写时明确上报，不虚报持久化成功、不重新执行业务操作。取消后保存部分证据同样使用独立收尾 context。
- 不提供通用“按旧 params 重放”。业务重试必须重新验证目标、权限、当前状态、配置及确认条件。

## 6. 数据与接口变更

使用新的 `0012_task_center_unification.sql` 完成增量升级；若实施前已有新编号迁移，顺延到下一空闲编号。`0001` 至 `0011` 保持不可变。

### 数据扩展

| 位置 | 变更及约束 |
| --- | --- |
| `task_center_schedules` | 继续存储自动化规则；增加 `schedule_type=cron|interval|none`、`interval_seconds`、`timer_enabled`、只读业务投影 `webhook_enabled`、`archived_at`。`enabled` 表示自动化总开关；周期字段按类型校验，none 使用空 Cron、UTC 和空 next_run_at。 |
| 规则唯一性 | 当前 `(node_id,kind,subject)` 唯一约束改为仅约束未归档行的部分唯一索引。已有规则及 ID 保留。全局 CD 的 node_id 为空，subject 为业务项目名；清理 subject 为空；两类节点项目使用对应项目名。 |
| `task_center_schedule_runs` | 保留旧 ID、task_id、triggered_by、error；增加 `status`、`reason_code`、`source_id`、`scheduled_for`、`actor_id`、`rule_snapshot`、`config_version`。schedule_id 允许空值以承接临时手动触发；外键改为 RESTRICT，禁止级联抹除历史。 |

| `tasks` | 增加可选 `parent_task_id` 及索引、默认空的 `result_error`。原状态、params/result、ID 和业务关联不变；不引入通用依赖图。 |

新触发快照紧凑序列化后上限 16KiB，只含规则参数、配置引用与必要元数据；不能截断保存。预先验证快照可保存后才认领，异常规则停摆并显式报错。

### HTTP 与前端类型

- 保留 `/api/v1/task-center/schedules` 及现有 CRUD、preview、run、runs 路径；页面称“自动化规则”。在原模型上增加周期类型、interval、timer_enabled、有效状态与归档信息，避免另建重复 CRUD。
- 旧 Cron 请求未带 schedule_type 时按 cron 处理；未带 timer_enabled 时保留原值，新建默认为 true。原 enabled 对已有镜像规则仍保持原启停效果。interval 不受五段 Cron 限制，none 不计算下一次时间。
- 配置更新必须带 expected_version；所有影响配置的操作均检查 RowsAffected。归档沿用 DELETE 的入口语义，实际写归档标记并返回原 ID；不删除运行历史。
- preview 接口按 kind 复用实际下一次时间算法：Cron 返回时区计算结果，interval 返回秒级时间，清理使用每日／每周 DST 算法；不能用普通 Cron 预览代替清理的执行时间。
- 规则列表默认排除已归档行，可通过 `include_archived=true` 查看；归档规则仍可按原 ID 查看详情和历史。旧记录缺失的历史快照不能用归档时的当前参数冒充。
- run 接口增加可选业务动作。旧镜像请求保持行为；CD 默认检查；其余动作通过 kind 能力与原业务确认校验。返回触发记录及可用 Task ID，未启动也可查询原因。
- kinds 返回支持的周期／触发方式、作用域和可用动作。专用表单按前端 kind 注册提供；禁止在通用表单继续写 `kind === 'image.update'` 分支。
- 触发历史和执行历史均返回 `{items,total}` 并支持 limit/offset、规则／节点／来源／状态筛选。旧 runs 未提供分页参数时保持原数组响应，通过显式分页参数进入分页响应。
- 执行记录支持 `status=active`（pending/running）和 `status=finished`（success/failed/canceled）；省略 status 保持现有全部状态行为。稳定排序采用 `created_at DESC,id DESC`。
- 任务列表、节点任务列表与 records 接口支持 `view=summary`，从 SQL 阶段排除 params/result；未指定时保留原响应。Task 详情返回完整结果、result_error 和父子关联。
- 前端查询键包含全部筛选、页码、页大小；使用共享页大小偏好和服务端 total。筛选／页大小变化回第一页，数据收缩时校正越界页码。保留 `/tasks#taskID` 深链。
- 继续使用 22xxx 业务错误码，补充超限／不支持动作／停摆原因；不在错误响应、SQL 日志、审计或快照中暴露敏感值。同步 API.md、业务说明与 demo/mock 行为。

## 7. 升级、切换与恢复

1. 以原迁移锁和事务执行增量结构升级。旧镜像规则保留 ID、参数、周期、启用状态和 next_run_at；新增 timer_enabled 为 true，由总开关保持原有效状态。
2. 从持久化清理策略建立规则，保留启用状态、民用时区和原 next_run_at；仅转换明确的每日／每周时间。授权缺失、版本冲突或配置无法转换时保持停用／停摆并列出原因，不自动授权或猜测。
3. 为已配置的全局 CD 及有效节点项目 CD 建立 interval 规则，原样保留间隔、自动化开关和 Webhook 状态。候选、首次确认、失败指纹、回滚策略、凭据及加密环境值均不改变。项目 CD 原有恢复暂停在规则创建／恢复时同步生效。
4. 旧触发记录有 Task 的标记为 started；旧启动错误标记为 start_failed；无可靠证据的记录标为 interrupted 并注明历史不完整。不推断旧 scheduled_for、actor、规则快照或授权。
5. 不为过去的清理／CD 运行制造通用触发记录；原业务历史通过原 ID 和 Task 联查展示。旧完整结果继续可读，原加密密钥、应用文件、节点和凭据不改写。
6. 采用单实例停机切换：先停止接收新业务操作并等待活动操作结束，再停止旧实例；不得并行运行新旧控制平面。新程序在处理请求和启动任何周期循环前完成迁移及业务恢复；然后只启动中心扫描器。删除 cleanup、cd、projectcd 的独立周期派发循环，保留各自中断恢复与停止资源逻辑，不保留双调度试运行开关。正常关闭时先停止中心接纳／派发，再停止业务资源，避免关闭过程中产生新任务。
7. interval 由最后检查时间加原间隔计算首次到期；过期时按一次当前检查处理。Cron 过期按停机跳过处理。已存在异常 enabled=true/next_run_at=NULL 的镜像规则保持停摆，须明确编辑恢复，避免猜测后自动启动。
8. 原业务删除／模式切换在同一持久化事务中停用或归档相关规则。删除节点时一并归档其节点规则，保留原节点名称、触发与 Task 证据。CD 接管继续阻止镜像自动重建，切回手动后按原镜像规则恢复其既有意图，不擅自开启原本关闭的规则。
9. 结构升级后，业务规则转换另以同一 advisory lock、单一事务及账本标记执行，只有四类转换全部成功才写完成标记并允许启动；重启不重复转换。转换失败回滚本次业务转换，保留已应用的结构迁移账本并阻止服务启动，不通过删表或退回旧扫描器恢复。迁移验证输出转换数量、停摆清单和旧新开关／间隔对照，不输出秘密。

上线前记录数据库与应用文件的现有备份位置并验证可恢复性，不引入自动备份功能。代码回退仅允许到已验证兼容新结构且关闭旧调度循环的修复版本；禁止直接回退到会重新启动旧扫描器的版本，禁止通过删除迁移账本回退。
